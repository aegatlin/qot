# A committed, Apple-native Xcode project

Status: decided
Date: 2026-11-08
Question: Should the Apple client's Xcode project stay generated by XcodeGen
and gitignored, or be committed and edited the way Apple's tools expect?

## Answer

Commit `client_apple/Qot.xcodeproj` and make it the source of truth; drop
XcodeGen. This supersedes the "Generated Xcode project" decision in
`2026-11-04-repo-layout-for-clients.md` (the rest of that record stands).

- Targets use Xcode 16's synchronized folders, so adding or renaming a file
  doesn't touch the project file.
- The `Qot` scheme is shared and archives.
- `Config/Signing.xcconfig` sets the team (Abstract Syntax LLC) and includes
  an optional, gitignored `Config/Local.xcconfig` where a contributor sets
  their own. The simulator needs no team.
- Xcode Cloud builds for TestFlight. `ci_scripts/ci_post_clone.sh` installs
  the Rust pinned in `mise.toml` and builds the Rust core, which stays built
  from source rather than committed.
- GitHub Actions (`apple.yml`) stays the check on every pull request.

The general rule, for every client: **use the platform's native project
format, committed, so a fresh clone opens in the platform's own IDE and its
own CI.** For Android that will be a committed Gradle project with the
wrapper, opened in Android Studio, with the Rust core built by a Gradle task
or `cargo-ndk`. The Rust core is the one thing outside each platform's
toolchain, and it is built by one documented command.

## Why

The XcodeGen decision (2026-11-04) was made before shipping was considered.
Its reasons were that agents edit `project.pbxproj` badly and that Tuist is
too heavy. Setting up Xcode Cloud showed the cost:

- **Xcode Cloud reads the project and shared schemes from the repository.**
  With the project gitignored, the workflow editor refuses the scheme ("The
  scheme 'Qot' may only exist locally. To use it in this workflow, it must be
  pushed to your repository.") and won't save. Generating the project in
  `ci_post_clone.sh` doesn't help the editor, which checks before any build.
- **Apple assumes a committed project elsewhere too.** Xcode Cloud doesn't
  resolve Swift packages automatically; it reads `Package.resolved`, which
  must be committed at
  `<name>.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`.
  Its custom build scripts live in `ci_scripts` "in the same directory as
  your Xcode project".
- **Apple steers away from third-party build tools**: "review and simplify
  your third-party dependencies", prefer Swift packages, and fall back to a
  post-clone script with Homebrew only when needed.
- **The original reasons have mostly gone.** Synchronized folders removed the
  main source of pbxproj churn and merge conflicts (file references). Agents
  now have Xcode's own tools (the Xcode MCP: new targets, entitlements,
  Info.plist keys, build settings) instead of hand-editing the pbxproj.
- **qot is open source.** A contributor should clone, open `Qot.xcodeproj`
  and run, without first installing a generator. Xcode Cloud doesn't build
  pull requests from forks (a public request from Wikimedia is open; no
  Apple statement says otherwise, unverified), so the PR check stays on
  GitHub Actions and Xcode Cloud only delivers builds.
- **More Apple platforms are coming** (Mac, maybe visionOS and tvOS). Adding
  a target with File > New Target, and capabilities through automatic
  signing, is the path Apple's templates and documentation assume.

## Options considered

| Option | Verdict |
|---|---|
| Keep XcodeGen, generate in `ci_post_clone.sh` | Rejected: the workflow editor still can't see the scheme; Apple-tool friction everywhere else stays |
| Keep `project.yml` and also commit the generated project, CI checks they match | Rejected: two sources of truth; edits made in Xcode (signing, Xcode Cloud setup) would be overwritten by the next generation |
| Tuist | Rejected: heavier still, and the same mismatch with Apple's tools |
| **Commit the project, synchronized folders, no generator** | Chosen |

For the Rust core under Xcode Cloud:

| Option | Verdict |
|---|---|
| **Build it in `ci_post_clone.sh`** (mise from Homebrew, the pinned Rust, `scripts/build-apple-core --release`) | Chosen: same build as a developer's Mac; costs some Xcode Cloud compute time |
| Commit `QotFFI.xcframework` | Rejected: binaries in git on every Rust change |
| Publish it as a remote `binaryTarget` (URL and checksum) from GitHub Releases | Deferred: lets Swift-only contributors skip Rust, but adds a release step to every Rust change. Revisit if contributors ask |

## How it was done

The last XcodeGen run generated the project with
`defaultSourceDirectoryType: syncedFolder` and the signing xcconfig, so the
committed project starts in its final shape; then `project.yml` and
XcodeGen were removed from the repo, `mise.toml` and CI.
