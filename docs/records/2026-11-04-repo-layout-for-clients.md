# Repo layout for many clients

Status: decided (its generated Xcode project part superseded by
`2026-11-08-apple-native-project.md`)
Date: 2026-11-04
Question: How should the repo's top level be organized so it holds the CLI,
iOS, watchOS, macOS, Android, Wear OS, the web, and whatever comes after
(TVs, fridges, hardware), without a reshuffle each time?

> **Since then:** XcodeGen, `project.yml` and `mise run gen:apple` are gone.
> `client_apple/Qot.xcodeproj` is committed, and a fresh clone runs `mise run
> build:apple-core` (or `mise run xcode`). The folder layout below still holds.

## Answer

**One top-level folder per build toolchain, not per device.** Each device
or form factor is a target inside the folder for its toolchain. Folders keep
the existing `<role>_<platform>` naming:

```
core/            qot_core: pure Rust, no FFI or platform dependencies
core_ffi/        qot_ffi: UniFFI bindings (Swift now, Kotlin later)
core_wasm/       wasm-bindgen bindings for the web client (later)
client_cli/      Rust
client_apple/    one Xcode project (generated by XcodeGen): iPhone and iPad now;
                 widgets, intents, Watch and Mac as more targets.
                 QotKit/ is the SwiftPM package every target shares.
client_android/  one Gradle project: phone, Wear OS, TV as modules (later)
client_web/      the PWA (later); also the catch-all for platforms that
                 run web apps (fridges, TVs, Linux and Windows desktops)
client_desktop/  only if a cross-OS desktop app (e.g. Tauri) is ever built
client_<device>/ hardware, if it happens
server_web/      Phoenix sync server
```

Rules:

1. **A new device is a new target, not a new folder,** unless it brings a
   new toolchain.
2. **`core/` stays pure.** Each language gets a thin binding crate that
   adapts types and holds no rules. The functional core / imperative shell
   split applies to the repo layout too.
3. **mise tasks and CI follow folder names** (`test:apple`,
   `build:apple-core`, `gen:apple`). A CI workflow for a toolchain runs only
   when its folder or the Rust it links changes.
4. **The Mac app is native SwiftUI inside `client_apple`.** It shares most
   of its code with iOS (QotKit, intents, widgets).

## Why

- **Apple and Android build several devices from one project.** One Xcode
  project holds the iPhone app, its widgets, App Intents, the Control Center
  control, the Watch app and the Mac app, all sharing Swift packages. Split
  into `ios/`, `watchos/` and `macos/`, those folders would either reach into
  each other or copy code. Gradle groups phone, Wear and TV modules the same
  way.
- **What runs where follows the toolchain.** CI runners (macOS for Xcode),
  mise tools and what a Linux cloud session can check all depend on the
  toolchain, never on the device.
- **The capture surfaces are native.** App Intents, Control Center
  controls, the Action button, widgets, Wear tiles and Android Quick
  Settings tiles have no good cross-platform abstraction, and capturing from
  them is the product. Kotlin/Compose Multiplatform, Flutter, React Native
  or Skip would mostly replace the UI, which is the thin part. The shared
  logic is already in Rust, so a per-ecosystem native layer is what remains.
- **The long tail runs the web.** Most odd platforms (smart fridges run
  Tizen web apps, TVs, Linux and Windows desktops) are covered by one PWA,
  not by more folders.
- **Monorepo.** One PR changes the core, the bindings and every client
  together, and the shared rules can't drift between repos.

## Adversarial review

The proposal (folders named by device: `ios/` and `android/`) was reviewed
adversarially before deciding. What changed or got written down because of
it:

- **The Watch doesn't link qot_core in v1. (Severity: high.)**
  `aarch64-apple-watchos` is a Tier 2 Rust target. `arm64_32-apple-watchos`,
  which watches older than Series 9 still need and which a shipped Watch app
  must include, is Tier 3: nightly and `-Zbuild-std` only. That conflicts
  with the single pinned toolchain. So in v1 the Watch sends captured text to
  the iPhone over WatchConnectivity, and the phone creates the note (#35).
  Revisit once arm64_32 watches age out. *Not verified:* that automerge
  0.12 builds for arm64_32 under build-std.
- **Linux cloud sessions can't check the Apple code. (High.)** Logic that
  agents will touch goes in **QotKit**, a plain SwiftPM package (no UIKit or
  WidgetKit), tested with `swift test` against the real Rust core. The Xcode
  targets stay thin. Running QotKit's tests on Linux too is #33. Until then
  `test:apple` reports itself skipped off macOS.
- **The built framework is gitignored, and that is under-specified.
  (Medium.)** `scripts/build-apple-core` builds the XCFramework (iPhone,
  simulator and Mac slices; the Mac slice is what `swift test` on the host
  uses) and the generated Swift. QotKit references them as a SwiftPM
  `binaryTarget(path:)`. Committing the binary was rejected: it would bloat
  git with every Rust change. A fresh clone needs `mise run gen:apple` before
  opening Xcode. Release builds add the device-only slices (built by Xcode Cloud since 2026-11-08).
- **"apple" names a vendor, not a toolchain. (Medium.)** Accepted.
  - If Skip (Swift to Android) were adopted, Android would still get its own
    Gradle project.
  - A cross-OS desktop app would be `client_desktop/`.
  - The rule "the Mac app lives in `client_apple`" is stated outright above.
- **One UniFFI crate for Swift and Kotlin, separate from core. (Low.)**
  Kept. qot_core's immutable "return a new Note" API is wrapped by
  `Arc`-backed UniFFI objects that also never mutate. UniFFI is pre-1.0 and
  breaks things between minors, so it is pinned exactly (`=0.32.2`). The FFI
  is synchronous with no async exports (async has gaps in 0.32), and network
  I/O stays in Swift and Kotlin, which matches functional core / imperative
  shell anyway.
- **Shared test vectors. (Medium.)** Every binding should run the same sync
  scenarios as the Rust tests (#34).
- **`server_web` vs `client_web`. (Low.)** "web" means Phoenix in one and
  the browser in the other. Renaming `server_web` would churn CI, the
  Dockerfile path and Railway's watch pattern for little gain, so both
  names stay.
- **Generated Xcode project. (Low.)** Superseded by
  `2026-11-08-apple-native-project.md`. XcodeGen (`project.yml`; generated
  `.xcodeproj` gitignored) over a committed project:
  - Xcode 16's synchronized folders cut pbxproj churn, but targets,
    extensions and entitlements still live in pbxproj, which agents edit
    badly.
  - Tuist is heavier than a solo developer needs.
  - XcodeGen is maintained (2.46.0 in 2026) and pinned in `mise.toml`.

## Options considered

| Option | Verdict |
|---|---|
| By device: `ios/`, `android/`, `watchos/`, … | Rejected: splits one Xcode or Gradle project across folders |
| By toolchain, flat `client_<platform>` | **Chosen** |
| Nested `clients/<platform>`, `server/`, `core/` | Rejected for now: same idea, but moving the existing folders churns the workspace, mise, CI and Railway for no functional gain |
| `client_ios` instead of `client_apple` | Rejected: the Watch and Mac targets would live under a folder named after another OS |
| A cross-platform UI (KMP/Compose MP, Flutter, RN, Tauri mobile, Skip) | Rejected for mobile: the capture surfaces need native code anyway, and the shared logic is in Rust |
| Separate repos per client | Rejected: core changes would need coordinated releases across repos |
